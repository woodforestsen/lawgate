## 一、总体判断

先给结论，避免你被下面的清单误导：

**这个仓库的工程质量明显高于同类学生项目**，理由有三条，且都是可核实的：

1. **有偏差台账**：`docs/deviations.md` 记录 D0–D37 共 38 条偏差，每条写明"现象 / 根因 / 影响核心结论与否"。这不是装饰——本次审计中多个"看着像 bug"的写法（例如 `complexity.py` 里信号方向反了、`hybrid` 路由只对 b2 用神经信号）都在注释里标了 D 编号并解释了原因，**属有意为之**。
2. **诚实声明到位**：README §6 主动披露"案号库全是合成数据""法条非官方原文""无人工标注员、κ 来自模拟标注员""E3 是负结果"。这种自我限定的写法在参赛项目里很少见。
3. **核心链路设计干净**：`router.py` 把 `answer()` 与 `answer_stream()` 收敛到唯一的 `_answer_events()`，避免"界面走 B、接口走 C"的口径漂移；全确定性意图检测不依赖模型。

**所以对"是不是全部都有用"的直接回答是：绝大部分有用，没有大面积的废弃代码。** 冗余集中在 1 处文件副本、3 个被取代的脚本、约 20 个死函数。

**对"代码写得是否正确"的回答是：主链路逻辑正确，但存在 4 个高严重度问题**——其中第 1、2 条会直接影响对外展示和演示，第 3、4 条会让"验收通过"变成假象。下面按严重度排列。

### H1. 配置与 README 全面矛盾：默认后端实际是本地 6.7B，不是 DeepSeek API　【已验证】

| 位置 | 内容 |

| `README.md:33` | 「最终回答模型 ✅ **DeepSeek 官方 API 的 `deepseek-v4-flash`（默认）**」 |
| `README.md:191` | 「单条 192 token 约 **1–3 s**」 |
| `README.md:34` | 「门控草稿来源 ✅ 本机 Qwen2.5-0.5B（默认）；**与回答模型不同源**」 |

**矛盾点有两处**：

1. **后端**：README 全篇（§0、§1、§6 第 3 条）声称默认走 API、单条 1–3 秒；实际配置是本地 6.7B，在 CPU 上按 README 自己的 D29 口径是**单栏 192 token 约 2–4 分钟**。照 README 的预期去演示，会以为卡死了。
2. **草稿来源**：`base.yaml:13` 注释说"回答与草稿都用同一份 6.7B"，而 README:34/700-703 说"草稿是本机 0.5B、与回答模型不同源"。这是**门控信号的口径原点**——u 的分布直接由草稿模型决定，而 E1–E5 的全部数字都建立在"草稿=0.5B"上。

**为什么算高严重度**：README §4 的 E1–E5 全套结论、§6 的口径三件套（`回答=API deepseek-v4-flash / 草稿=本机 0.5B / 192 tokens`）都以"API 后端"为前提。现在配置回退到本地权重，**答辩时如果被问"你现在跑的是哪套"，按 README 回答就会说错**。

**建议**：二选一，别让两者并存——
- 演示前把 `base.yaml:16` 改回 `deepseek`（或演示时用 `启动服务.ps1 -LlmBackend deepseek` 显式覆盖）；或
- 在 README §0 顶部加一行醒目提示，写清"仓库当前配置为离线兜底（hf 6.7B），E1–E5 数字的 API 口径为历史口径"。

### H3. 双栏界面并发调用同一个 HF 模型实例　【已验证，当前默认配置即触发】

`lawgate/api/ui.py` 的双栏对照是**同一个模型对象被两个线程同时用**：

- `ui.py:74` — `STATE["base_llm"] = ctx.llm`（左栏用的就是 router 的 llm）
- `ui.py:219-254` — 左栏丢进后台线程 `_left_worker`，在 `ui.py:223` 调 `STATE["base_llm"].generate_stream(...)`
- 右栏在同一时刻由 Gradio 主线程调 `router` 里的**同一个** llm 生成
- `lawgate/channel/llm_base.py` **全文件没有任何锁**（`grep -n "Lock\|_lock"` 只命中 `import threading` 与流式用的 `threading.Thread`）

**为什么现在特别危险**：H1 提到当前默认 `llm_backend: hf`。走本地权重时，两栏并发进入同一个 `transformers` 模型的 `generate()`，会争抢 KV cache 与 `TextIteratorStreamer`，输出可能互相串扰。走 DeepSeek API 后端时无此问题（HTTP 调用天然并发安全）——**所以这个 bug 是"改配置才暴露"的，恰好和 H1 叠在一起**。

**次要隐患**：`ui.py:219-254` 没有取消传播。客户端中途取消时，消费者提前退出，后台线程与 HF 的 streamer 线程会继续跑完，无界 `queue.Queue` 继续累积；反复取消会叠加并发生成。

**建议**：给 `HFLLM` 加一把生成锁（`threading.Lock` 包住 `generate`/`generate_stream` 的模型调用段），或在 UI 层保证双栏串行。

### H4. 三个验收脚本的退出码恒为 0，"验收 PASS"可能是假象　【已验证】

| 位置 | 代码 | 问题 |
|---|---|---|
| `scripts/e1_plot.py:205` | `return 0 if assertion.get("status") in ("PASS", "SKIP") else 0` | **三元两个分支都是 0**——核心断言 FAIL 时进程仍以 0 退出 |
| `scripts/quickcheck.py:135` | `return 0` | 恒 0 |
| `scripts/intent_accept.py:196` | `return 0` | 恒 0，而 `:117` 算了 `recall_pass`、`:147/:195` 明明打印了 PASS/FAIL |

**为什么要紧**：README §1 第 4 步明确写「⚠️ 控制台是 GBK，中文输出会乱码 —— **只看退出码**，内容去 `docs/quickcheck.txt` 看」。也就是说你自己给的操作指引就是把退出码当验收信号，而这三个脚本的退出码**永远不反映失败**。断言一旦回归，不会有人发现。

**对照组**：其余验收脚本（`check_stream.py` / `check_deepseek.py` / `check_fuzi_e2e.py`）的退出码语义是对的，说明这是漏改而不是设计。

**修法**：`e1_plot.py:205` 改成 `return 0 if assertion.get("status") in ("PASS", "SKIP") else 1`；另两个把 `recall_pass` / 各段 `ok == total` 汇成布尔后返回。

## 三、中严重度问题（5 条，影响测量效度与数据完整性）

### M1. `cited_golden` 仍是双向子串匹配，D34 的修复没同步过来　【已验证】

```python
# lawgate/eval/metrics.py:170
law_hit = any(law in l or l in law for l in cites["laws"]) or law in "".join(cites["laws"])
```

- `metrics.py:65-81` 已经实现了严格版 `_law_hit()`，注释写明是为了解决 **"劳动合同法"里含"合同法"导致误命中**（D34-②）。
- 但 `cited_golden` 没用它，仍然是双向子串匹配 → **答案引用了《劳动合同法》会被记成命中了 golden《合同法》**。
- 影响方向：**高估引用命中率**，即"利好本项目"。这不是准确率（acc）指标，但属于测量效度缺陷，且和 `docs/annotation_guide.md` 声称的"法律名 + 条号同时命中"口径不符。

**修法**：`cited_golden` 里的这一行换成 `any(_law_hit(law, l) for l in cites["laws"])`，然后按 D34 的既定流程**统一离线重判**（`scripts/rescore_results.py`），因为你改的是判分器，不改会与存量结果不可比。

### M2. `plotting.py:1115` 的 `lac` 派生方向反了　【已验证】

```python
# lawgate/eval/plotting.py:1105-1115（由逐条记录派生）
if metric in ("rr", "lac"):
    used = _as_bool(row.get("retrieval_used"))
    val = 1.0 if used else 0.0
    return (1.0 - val) if metric == "lac" else val     # ← lac 被取反
```

而 `metrics.py:337` 的定义是 `lac = sum(n_retrieval_calls) / n`（**平均检索调用数，越大检索越多**），`:357` 注释也写「lac = 平均检索调用数」。取反后派生出的是"未检索比例"，**与聚合口径完全相反**。

覆盖面：`plot_ablation(...)` 的默认参数恰是 `metric: str = "lac"`（`plotting.py:1126`）。只要图走的是"由逐条记录派生"分支，消融图的数值含义就是反的。

### M3. 重建知识库会把 FLK 核验状态抹回"未核验"　【已验证】

```python
# lawgate/knowledge/build_sqlite.py:161-169
conn.execute("""INSERT OR REPLACE INTO ingest_provenance
   (law_short,version,source_kind,source_url,retrieval_date,verification,
    n_provisions,continuity_gaps,note) VALUES (?,?,?,?,?,?,?,?,?)""",
   (short, spec["version"], "MANUAL_TRANSCRIPT", spec["source_url"], TODAY,
    "PENDING_FLK_VERIFICATION", ...))
```

- `source_kind` / `verification` **硬编码**，且 `INSERT OR REPLACE` 的字段列表里**不含 `verified_by` / `verified_date`**（REPLACE 会整行删掉重插）→ 人工核验痕迹全丢。
- README §3 把 `scripts/import_law_text.py` 标为「**申报前必做**：导入 FLK 官方原文，升级 `verification=VERIFIED`」。
- **如果你的操作顺序是"先 import_law_text 升级 → 之后再跑 build_sqlite 重建库"，核验状态会被静默抹掉，申报时提交的又是 `PENDING_FLK_VERIFICATION`**。

**建议**：要么把 `verification` 改成"仅当该行不存在时写入"（`INSERT ... ON CONFLICT DO UPDATE SET source_url=..., n_provisions=...`，不动 verification），要么干脆从 INSERT 列里去掉这两列。同时补一句注释写明"必须先 build_sqlite 再 import_law_text"的正确顺序。

### M4. 向量库降级路径会累积重复向量　【已验证】

- `lawgate/knowledge/build_vector.py:96-101`：只有 `backend == "numpy"` 时才删旧文件（`embeddings.npy` / `records.jsonl`）。
- 但默认 `backend="auto"`。chromadb 不可用时 `get_store()` 降级到 `NumpyStore`，其 `__init__` 会先 `load()` 旧矩阵（`store.py:72-86`），而 `add()` 是 `np.vstack` **追加**（`store.py:89-99`）→ **每重建一次索引就翻一倍**。

本机 chromadb 可用，所以是隐患而非现状；但"检索结果突然出现大量重复文档"时会很难查。

**修法**：把 96 行的条件从 `backend == "numpy"` 改成"按 `store.backend` 实际值判断"，或直接无条件清空旧产物（`get_store` 之后再删）。

### M5. DeepSeek 后端拿到空正文时不兜底　【已验证】

- `deepseek_llm.py:368-382` 的 `_from_completion` 只做 `content.strip()`，没有对空内容做任何处理。
- `deepseek_llm.py:399-427` 的 `generate_messages`：拿到 `text = ""` 后直接 `self.cache.put(...)` 写进缓存（`:420-425`）并 `return text`（`:427`）→ **空答案被缓存冻结，后续同一问题永远秒回空**。
- 模块自身的注释说「绝不能让上层看到答案莫名其妙是空的」，而 README:195-198 承认了"思考模式下正文为空"的现象，靠"默认关思考"规避。——**规避了默认路径，但没有实现防御**。一旦有人设了 `LAWGATE_LLM_THINKING=1` 且 max_tokens 偏小，就会静默返回空串并被缓存。

**建议**：`generate_messages` 里加一条——`if not text and body["reasoning"]: 报错或降级`（并**不要**把空串写入缓存）。
