## 第 1 章 这个项目到底在做什么（一分钟比喻版）

想象你开了一家**法律咨询工作室**。客人问的问题五花八门：

- "《担保法》现在还有用吗？" —— 这不该靠记忆回答，该**翻法典**（查工具书，100% 准确）；
- "（2099）沪01民终88888号是什么案子？" —— 该**去裁判文书库核对案号真假**；
- "什么是离婚冷静期？" —— 常识性问题，律师**直接口头解答**就行，翻书浪费时间；
- "违约金过高法院会怎么调整？" —— 介于两者之间，凭记忆答容易编错法条，
  最好**先搜相关材料再答**。

本项目（代号 **CA-LegalGate**，中文名"律核"）就是把上面这家工作室**自动化**：

| 干活方式 | 系统里的名字 | 比喻 | 检索次数 |
|---|---|---|---|
| ① 直接翻结构化数据库，把条文/核验结论拼成答案 | **通道 B**（确定性结构化） | 查字典 | **0 次** |
| ② 什么都不查，让 AI 大模型凭"记忆"直接写答案 | **通道 A**（直接生成） | 口头快答 | **0 次** |
| ③ 先用向量检索找出最相关的法条/文书片段，喂给 AI 参考着写 | **通道 C**（语义检索增强） | 先复印相关资料再作答 | **1 次** |

**一次提问只走一条通道**。走哪条，由两道"闸门"决定：

1. 先看**问题里有没有明确的"查库信号"**（提到具体法名+条号、具体案号……）→ 有就走通道 B；
2. 没有的话，做一个**便宜的"试探"**：让 AI 先打 20 个字的草稿，看它"心虚不心虚"
   （术语叫不确定性信号），再结合问题的复杂度打分，跟一个**校准过的阈值**比大小
   → 心虚就走通道 C（查了再答），不心虚就走通道 A（直接答）。

三个卖点，说人话就是：

- **免训练（training-free）**：一行模型训练代码都没有，不用显卡训练，全靠"流程设计"；
- **省钱（少检索）**：能直接答的不去检索，能查字典的不去复印整本书——但准确率不降；
- **可审计（trace）**：每次回答都附一份"决策记录"：走了哪条通道、为什么、
  门控分数是多少、阈值是多少、引用了哪部法律哪一条、链接出处在哪。答辩/检查时逐条可查。

技术栈一句话：**Python + FastAPI（接口）+ Gradio（演示界面）+ SQLite（法条事实库）+
ChromaDB（向量库）+ 本机 **Qwen3-4B**（默认用它回答）+ bge 向量模型**，全程 CPU 也能跑
（想更快可切 DeepSeek API：`启动服务.ps1 -LlmBackend deepseek`，见 5.4）。

## 第 2 章 核心思想图解：为什么是"三条通道 + 一道门"

### 2.1 要解决的矛盾：RAG 的"检索悖论"

现在流行的法律 AI 问答都用 **RAG**（Retrieval-Augmented Generation，检索增强生成）：
先搜资料、再让大模型照着资料答。它准，但有两个毛病：

1. **每问必搜很贵**：检索系统本身要钱、要算力、要延迟；
2. **不该搜的时候搜了反而帮倒忙**：问"什么是诉讼时效"这种常识，搜回来的杂乱片段
   可能把模型带偏。

反过来，**完全不搜**（纯让模型凭记忆答）会**编造法条**——这在法律场景是致命的。
本项目实测的"杀手级翻车案例"：直接问小模型"《合同法》第 52 条"，它会一字不差地
**原文背诵一部已经废止的法律**，还装作现行有效。

### 2.2 本项目的解法：把"搜不搜"变成一道可校准的门

整体决策流水线（每一问从上到下走一遍）：

```
用户提问 (+历史对话 + 可选评估日期)
   │
   ▼
┌─────────────────────────────────────────────────────────┐
│ 第 1 步 意图检测（纯规则，正则表达式+词典，不用 AI）      │
│   能从问题里抽取出「法名+条号」或「案号」或「法律名+时效问法」│
│   或「主题词+要法条的意图」吗？                            │
└─────────────────────────────────────────────────────────┘
   │ 能且槽位齐                        │ 不能
   ▼                                  ▼
┌──────────────────┐        ┌──────────────────────────────┐
│ 第 2 步 通道 B    │ 查不到  │ 第 3 步 门控（Gate）          │
│ 直接 SQLite 查询  │───────▶│  a) AI 先写 20 token 草稿      │
│ 拼条文/时效/核验  │  降级    │     → 算"不确定性" u_signal   │
│ (0 次检索)       │        │  b) 规则算复杂度   u_complexity│
└──────────────────┘        │  c) 问题分桶 b1~b4            │
   │ 命中                   │  d) 查该桶的校准阈值 τ_b       │
   ▼                        │  e) u > τ_b ? → 走 C : 走 A    │
 出答案+trace               └──────────────────────────────┘
                                     │            │
                              u>τ_b ▼            ▼ u≤τ_b
                          通道 C(检索1次+生成)  通道 A(直接生成)
                                     │            │
                                     ▼            ▼
                                  出答案+trace（统一格式）
```

### 2.3 三个关键设计决策（也是论文的"贡献点"）

1. **三通道异构**：A/B/C 不是同一类东西的三个档位，而是**三种完全不同的 machinery**
   （查库 / 参数记忆 / 向量检索），各自擅长的问题类型不重叠。
2. **桶级阈值校准**：门控阈值 τ 不是一个数，而是**按问题类型分 4 个桶、每桶单独校准**
   （概念题一个阈值、法条题一个阈值……）。校准方法：在 dev 集上找
   "精度不高于全检索基线太多、但检索量最小"的那个点（详见 7.6）。
3. **混合闸门**：法条题（b2）用"AI 草稿的不确定性信号"，其它桶改用
   "确定性复杂度评分"——这不是拍脑袋，是 E0 诊断实验**实测出来的**：
   神经信号只在法条题上有效（AUC 0.82），在概念题/多轮题上**反向**（AUC 0.19~0.36）。
   这就是著名的"辛普森悖论"（第 9 章故事 5 详述）。

## 第 3 章 术语小词典

按"读本文档时遇到就回来查"的方式组织，不必先背。

| 术语 | 大白话解释 |
|---|---|
| **大模型 / LLM** | 一个"文字接龙"程序：给它一段话，它一个 token 一个 token 地把后面的内容接出来。本项目最终回答默认用**本机权重 `models/Qwen3-4B`**（= 魔搭社区的 `Qwen/Qwen3-4B`，约 4B，CPU fp16，**离线**，见 D38）；想更快可切 **DeepSeek 官方 API 的 `deepseek-v4-flash`**（联网调用，单条 1–3 秒）；没带 4B 权重时会降级到本机 **夫子·明察（fuzi-mingcha-v1_0，6.7B，司法语料微调）**。 |
| **门控草稿** | 门控要问模型"你心里有底吗"，靠的是它写前 20 个 token 时的概率分布。**现行默认下这个草稿就是回答模型自己写的**（同一份权重，手册 S3.5 原设计：共享模型与前缀，prefill 不翻倍，D38）；只有回答切到 API 时才改由**另一个本机草稿模型**来写（历史上是 Qwen2.5-0.5B，原因见 5.4 末尾与 `docs/deviations.md` D30）。 |
| **token** | 大模型眼里的"字"。中文大约 1 个字 ≈ 1~1.5 个 token。生成 192 token ≈ 写 150~250 个汉字。 |
| **logprob（对数概率）** | 模型每写一个 token 前，会给词表里所有候选词打分（0~1 的概率，取对数后是负数，越接近 0 越自信）。它是"模型心里有没有底"的直接读数。 |
| **贪心解码（greedy）** | 每步只选概率最高的那个 token，不加随机。**同样的输入必然得到同样的输出**——整个系统可复现、可缓存的根基。 |
| **RAG** | 检索增强生成：先搜资料，把资料塞进提示词，再让模型照着答。 |
| **embedding（向量）** | 把一段文字压成一个 512 个小数组成的"坐标"，意思越接近的文字坐标越近。本项目用 bge-small-zh-v1.5 模型算向量。 |
| **向量库（ChromaDB）** | 存几万个"文字坐标"并支持"找离查询最近的 top-k 条"的库。 |
| **SQLite** | 一个文件就是一个数据库（`data/kb/legal_facts.db`），Python 自带支持，零安装。 |
| **FTS5** | SQLite 的全文检索扩展。⚠️ 本项目踩过大坑：它默认**不会把中文分词**，导致中文全文检索恒不命中（第 9 章故事 3）。 |
| **BM25** | 经典的关键词打分算法（搜索框那种），和向量检索互补，本项目用它做重排的一部分。 |
| **正则表达式（regex）** | 写字符串规则的语法，比如"匹配（2022）沪01民终12345号这种案号"。本项目的意图检测全靠它。 |
| **槽位（slot）** | 从问题里抠出来的结构化信息：法名、条号、款项、案号、主题词。 |
| **AUC** | 衡量"一个分数能不能区分两类样本"的指标，0.5=瞎猜，≥0.6 勉强可用，≥0.75 良好。E0 实验就是量这个。 |
| **τ（tau）** | 门控阈值。分数 u 和它比大小决定"搜还是不搜"。按桶存于 `configs/thresholds.json`。 |
| **dev / test 集** | 机器学习惯例：dev 用来调参数（校准阈值），test 用来最终打分，两者不许串。 |
| **SSE（Server-Sent Events）** | 一种服务器持续往浏览器推送的小协议：`event: xxx` + `data: {json}` 一帧一帧发。本项目流式输出用它。 |
| **FastAPI** | Python 最流行的写 HTTP 接口框架。`docs` 页面自动生成接口说明书。 |
| **Gradio** | 几十行代码拼一个网页界面的库，AI 演示界面无敌。 |
| **内容寻址缓存** | 把 prompt 做 sha256 哈希当钥匙，答案存 SQLite。下次同样的输入直接取答案，0 计算。 |
| **LoRA / 微调** | 本项目**没有**这些——"免训练"就是字面意思，一个梯度都没更新过。 |

### 4.2 记住一个原则：产物可重建，源不可丢

**源代码 + `configs/` + `data/raw/` + `models/`** 是要备份的；
`data/kb/`、`data/benchmark/`、`results/`、`figures/`、`docs/*.txt|md`（自检报告类）
全部可以按第 6 章的命令**重新生成**。删错了也不慌，重跑一遍就有
（只有阈值校准和实验结果要等 CPU 慢慢跑）。

## 第 5 章 环境准备（从零装到能跑）

### 5.1 Python

本项目实测环境：**Python 3.13（Anaconda 发行版）**。
小白推荐路线：装 [Anaconda](https://www.anaconda.com/download) 或 [Miniconda](https://docs.conda.io/en/latest/miniconda.html)。

⚠️ 一个与本机绑定的小坑：原仓库的 Anaconda 装在 `E:\Anaconda`。换机器时
`启动服务.ps1` 会找不到解释器——它已写好兜底（自动改用 `PATH` 里的 `python`），
若你有多个 Python，建议手动把 `启动服务.ps1` 第 40 行左右的
`$Py = 'E:\Anaconda\python.exe'` 改成你机器上的路径。

### 5.2 依赖包

本项目**没有 requirements.txt**（复现时建议自己补一份），实际用到的第三方库
（版本为原机器实测值，见 `docs/env_report.json`，同 major 版本即可）：

| 库 | 实测版本 | 干什么用 | 缺了会怎样 |
|---|---|---|---|
| torch | 2.11.0+cpu | 跑大模型 | 核心依赖 |
| transformers | 5.8.0 | 加载 Qwen、分词、生成、流式 | 核心依赖 |
| sentence-transformers | 5.5.1 | 加载 bge 向量模型 | 退化到哈希编码兜底（结果需标注） |

### 5.3 三个必须的环境变量（漏一个都可能"莫名崩溃"）

| 变量 | 值 | 为什么 |
|---|---|---|
| `KMP_DUPLICATE_LIB_OK` | `TRUE` | Anaconda 的 MKL 和 torch 都带 `libiomp5md.dll`（OpenMP 运行时），同时加载会**直接崩进程**。代码里 `lawgate/__init__.py` 也做了 setdefault 双保险。 |
| `TOKENIZERS_PARALLELISM` | `false` | 关闭分词器多线程 fork，否则警告刷屏。 |
| `HF_HUB_OFFLINE` | `1` | 原机器网络有中间层劫持导致 huggingface 证书校验失败（D0），强制只走本地权重。你在新干净网络机器上可设 0，但**不联网就保持 1**。 |

每次打开新 PowerShell 窗口都要设（或直接用第 6 章的启动脚本，它会自动设）：

```powershell
$env:KMP_DUPLICATE_LIB_OK   = "TRUE"
$env:TOKENIZERS_PARALLELISM = "false"
$env:HF_HUB_OFFLINE         = "1"
```

> ⚠️ **仓库根目录还有一个 `.env` 文件，它现在真的会被代码读**（这一点很重要）：
> 由 `lawgate/env_setup.py` 的 `apply()` 在 import 时读入（`import lawgate` 就会触发），
> 所以 `DEEPSEEK_API_KEY` 之类的设置**写在 `.env` 里就生效**，不必每个新窗口手工设环境变量
> （早期必须手工设，导致"换个终端就莫名 401"）。
> **优先级：真实环境变量 > `.env`**——已经存在的环境变量绝不会被覆盖，所以命令行、
> 启动脚本 `-LlmBackend` 的临时覆盖永远优先。想临时**完全不读**它：`$env:LAWGATE_DOTENV="0"`。
> ⚠️ **该文件含 API 密钥：不要外传、不要提交**（`.gitignore` 已经排除 `.env`）。

表里那三项（`KMP_DUPLICATE_LIB_OK` 等）是**进程级引导变量**，由同一个 `apply()` 兜底设置，
不写进 `.env` 也能跑。`.env` 里放的是**可选的运行开关**，常用几个：

| 变量 | 作用 | 默认 / 留空 |
|---|---|---|
| `DEEPSEEK_API_KEY` | DeepSeek 密钥（**只有把回答切到 API 时才需要**；默认走本机权重，不填也能跑） | 无（缺失时切 API 会报 401） |
| `DEEPSEEK_BASE_URL` | API 地址 | `https://api.deepseek.com` |
| `DEEPSEEK_MODEL` | 走 API 时的回答模型名 | `deepseek-v4-flash` |
| `LAWGATE_LLM_PROVIDER` | 回答模型从哪来：`hf`（本机权重，**现行默认**）/ `deepseek`（API，可选加速）/ `rule` | 按 `configs/base.yaml: llm_backend` |
| `LAWGATE_LLM_THINKING` | 思考模式（**仅 API 回答时相关**）：**留空或 0 = 关**（默认，1–3 秒出正文）；设 1 会先生成一大段推理，慢且小 `max_tokens` 时正文可能是空的 | 关 |
| `LAWGATE_LLM_TIMEOUT` / `LAWGATE_LLM_RETRIES` | 单次超时（秒）/ 失败重试次数（429、5xx、超时才重试） | `120` / `3` |
| `LAWGATE_DRAFT_SOURCE` | 门控草稿来源：`auto`（本机草稿 → API → 伪分布）/ `local` / `api` / `none` | `auto`（回答走本地时此开关不参与决策，草稿=回答模型本身） |
| `LAWGATE_DRAFT_MODEL` | 草稿模型路径；设 `none` = 不加载任何本地草稿模型 | 自动挑 `models/Qwen3-4B`（D38；仅"回答切 API"时才真正加载） |
| `LAWGATE_DOTENV` | 设 `0` = 完全不读 `.env` | `1` |
| `LAWGATE_MODEL` / `LAWGATE_EMBED` / `LAWGATE_DTYPE` | 回答模型 / 向量模型 / 精度（本地权重后端用） | 按 `base.yaml` |

> 关于联网：`.env` 里那行 `HF_HUB_OFFLINE=1` 和 `configs/base.yaml` 的 `allow_network: false`
> **只约束"从 HuggingFace 下载权重"**（本机对 HF 有中间层劫持，D0）。
> **现行默认（本机 Qwen3-4B 回答 + 同权重草稿）全程离线**，不需要任何网络；
> 只有你主动切 `-LlmBackend deepseek`（可选加速，见 5.4）时才需要联网——那是设计内的网络行为。

### 5.4 模型权重（回答模型、草稿模型、向量模型）

**先说结论**：默认配置下"最终回答"由**本机权重 `models/Qwen3-4B`** 产生
（= 魔搭社区的 `Qwen/Qwen3-4B`，约 4B，fp16/CPU，**2026-09-13 起为默认**，见 `docs/deviations.md` D38），
**门控草稿与它是同一份权重**（手册 S3.5：共享模型与前缀），所以本机真正会用到的只有两样：
**`models/Qwen3-4B`（约 8 GB）** 和 **向量模型 `bge-small-zh-v1.5`（约 95 MB）**。

| 目录 | 内容 | 来源 | 大小 | 默认需要吗 |
|---|---|---|---|---|
| `models/Qwen3-4B/` | **Qwen3-4B**（约 4B，3 个 safetensors 分片）——**"最终回答"用的就是它**，同时**也是门控草稿模型**（回答走本地时草稿直接复用回答模型本身，手册 S3.5） | **魔搭 ModelScope `Qwen/Qwen3-4B`**，用仓库自带脚本 `scripts/download_modelscope.py`（断点续传） | **~8.1 GB** | ✅ **默认需要**（不想下就切 API，见下） |
| `models/bge-small-zh-v1.5/` | BAAI 中文向量模型（512 维），给"语义检索通道"用 | HuggingFace `BAAI/bge-small-zh-v1.5`（或 `scripts/fetch_hf_files.py`） | ~95 MB | ✅ 必须 |
| （无需下载） | **DeepSeek API 的 `deepseek-v4-flash`**——**可选加速路径**，跑在云端（单条 192 token 约 1–3 秒） | DeepSeek 开放平台（只需在 `.env` 填 `DEEPSEEK_API_KEY`），启动时加 `-LlmBackend deepseek` | 0 | ❌ **不是默认**（想要快/要联网演示才用） |
| `models/fuzi-mingcha-v1_0/` | **夫子·明察**（司法大模型，ChatGLM-6B 底座，6.7B，15 个权重分片）——**降级兜底**的回答模型（没带 4B 权重时才轮到它） | ModelScope `furyton/fuzi-mingcha-v1_0`（仓库自带下载脚本 `scripts/_download_fuzi.sh`，断点续传） | **~13.4 GB**（fp16） | ❌ **默认不需要** |
| `models/qwen2.5-*` / HF 缓存里的 `Qwen/Qwen2.5-0.5B-Instruct` | **历史口径**的草稿/回答模型（D9/D21/D30），现已被 Qwen3-4B 取代，只在复现旧口径时手动指定 | HuggingFace（0.5B 已在原机器 HF 缓存 `E:\ModelCache\huggingface\hub` 里） | ~1 GB | ❌ 不需要 |

## 第 7 章 逐模块精讲

> 每个模块按同一个套路讲：**它解决什么问题 → 具体怎么实现 → 为什么这样设计**。
> 想读代码时从 ★ 文件开始。

### 7.1 ★ config.py —— 总配置与"我到底在用哪个模型"

**做什么**：全系统唯一的"路径+模型+默认参数"来源，并记录**运行环境指纹**。

- 所有路径相对仓库根：`data/kb/legal_facts.db`、`data/kb/chroma` 等；
  `configs/base.yaml` 的顶层 `key: value` 会逐条覆盖 Settings 字段。
- 模型候选顺序（这就是"自动解析"的全部秘密）：
  `models/Qwen3-4B` → `models/fuzi-mingcha-v1_0` → `models/qwen2.5-1.5b-instruct` →
  `models/qwen2.5-0.5b-instruct` → HF repo id → 本机 HF 缓存快照 glob；
  目录必须**同时**有 `config.json` 和真权重文件（`_has_weights`）才算可用。
  （Qwen3-4B 是**现行默认**，D38；后面几个是历史候选，本机谁还在就自动可用。）
- `provenance()`：把"硬件/设备/因果模型/精度/来源/向量模型/后端/日期/版本"打包成 dict，
  **每个结果文件、每张图的图注都自动嵌它**——这是"可审计"承诺的底层支撑。
- 无 PyYAML 时用一个 30 行的极简 key:value 解析器兜底（依赖最小化思想）。
- `dtype`：权重精度（**只对本地权重有意义**，走 API 回答时不用本机权重）。CPU 上的 `auto` 会落 fp32；
  **现行默认的 4B 在 CPU 上必须显式 `float16`**（fp32 约 16 GB vs fp16 约 8 GB），
  6.7B 的夫子·明察兜底同理（fp32 要约 27 GB），故 `configs/base.yaml` 里写死 `dtype: float16`。
- `model_source`：记录"这个模型路径是怎么定下来的"（显式配置 / 环境变量 / 自动挑选 / 缓存兜底），
  `scripts/check_backend.py` 会打印它——专门用来防"配置写 A、实际跑 B"的口径漂移（D21、D29）。

**设计细节**：为什么本地目录优先而不是 HF 缓存？因为 `models/` 是项目组手动审核过的权重，
缓存快照可能被别的程序污染；`_has_weights` 检查源于真实事故——权重下载一半时
`from_pretrained` 直接崩（注释里写明了）。

### 7.2 cache.py —— 内容寻址缓存（CPU 机器的算力基石）

**做什么**：把每次"生成/草稿"的输入 prompt 做 sha256，答案存进 SQLite
（`data/kb/gen_cache.db`，WAL 模式，线程本地连接+写锁）。

**密钥构造**：`sha256(model | kind | max_tokens | prompt全文)`。这个设计一石三鸟：

1. **换模型自动失效**（model 进了哈希，不会拿旧模型的旧答案冒充新模型）；
2. **跨方法复用**：E1 的 6 个基线里 many 方法的 prompt 完全相同
   （neverrag/legalgate 通道A/…都调 `llm.generate(context=None)`），
   缓存把这些重复从 ~1.5 万次折叠到 ~1.7 千次——**没有它，实验在 CPU 上根本跑不完**；
3. **可审计**：缓存表本身就是"每条 prompt 都算过什么"的账本（含 token 数、秒数）。

**细节**：贪心解码是确定性的，这是缓存正确性的前提（偏差 D8 专门澄清：
seed 在贪心下只影响数据划分与 bootstrap 重采样，不影响单条生成）。

### 7.3 知识库（schema / 种子语料 / 解析器 / 审计 / 建库）

**表结构**（`schema.sql`，10 张表，逐列含义看注释）：

| 表 | 内容 | 关键设计 |
|---|---|---|
| `legal_provisions` | 法条**按款项拆行**：一条 3 款 5 项 = 3+5 行 | `UNIQUE(法,版本,条,款,项)`；`item_no` 默认 `''` 不用 NULL（SQLite 里 NULL 互不相等会击穿唯一约束，D2）；`validity_status` CHECK 枚举五态；`superseded_by` 存 `民法典#667` 这种替代指针 |
| `provision_fts` | FTS5 全文表 | 带 `provision_id UNINDEXED` 精确回连，避免一条多项 JOIN 出重复行（D1） |
| `provision_keywords` | 关键词→(法,条) 反向索引 | 建库时扫描现行有效条文正文 `LIKE '%关键词%'` 生成；**这是 P4 主题检索的救命方案**（见 7.7 和 D26-3） |
| `case_registry` | 案号真值库（600 条合成） | `data_source='SYNTHETIC'` 列强制披露 |
| `judgments` | 合成文书全文+分块 JSON | 同上 |
| `law_lifecycle` | 沿革边表：from_law→to_law+关系+生效日 | 时效状态机的图数据 |
| `law_alias` / `topic_keyword` | 词典下沉到库里 | 法学生改库=改词典，不用改代码 |
| `ingest_provenance` / `parse_audit` / `case_verify_log`（schema_ext.sql） | 溯源三表 | 每部法"哪来的、验没验、缺哪些条号"全部落库 |

**种子语料 `seed_corpus.py`（重要！条文原文就存在代码里）**：
`LAW_SPECS` 共 **13 部法**：民法典(62 条关键条文)、合同法、公司法(2024 新)、
公司法(2018修正)、劳动合同法、民事诉讼法、民法典时间效力规定、物权法、担保法、
婚姻法、侵权责任法、继承法、收养法（后 6 部均 `validity_status=已废止`，专门用于时效陷阱）。
每部法带元信息（law_name/law_level/version/effective_date/publish_date/source_url）+
多行字符串形式的条文原文。**为什么人工录入？** 原机器网络被中间层劫持，
法律文本"宁可手工转录+标记待验证，也不从不可信通道抓"（D0）。
`LIFECYCLE_SEED`（8 条沿革边）与 `SUPERSEDE_MAP`（旧法条→民法典新条映射，如
合同法52→民法典143/153、公司法2018第26条→新公司法47）共同支撑通道 B 的"替代指引"。

**合成案号 `seed_cases.py`**：真实案号格式=（年份）法院代字+类型代字+序号+号，
如（2022）沪01民终12345号。生成器用 15 个真实法院代字 × 3 类民事审级 × 4 案由、
`random.Random(42)` 固定种子造 600 条，并给每条渲染一篇极简"判决书"
（模板化案情+说理，文末自带"合成数据"声明）。**合成 ≠ 造假**：所有下游消费点
（trace、答案尾注、评测集字段、E6 报告）都必须显式披露 SYNTHETIC。

**解析器 `flk_parser.py`（一个手写状态机）**：
逐行走：`第X条` 开新条 → 自然段是新"款" → `（一）` 行是"项" → 编/章/节行切结构。
几个魔鬼细节（全部来自真实 bug，见 `docs/deviations.md` D3~D7）：

1. **不做 NFKC 归一化**！那会把全角逗号变半角，**篡改法条原文**——法条库的全部价值在保真；
2. 合并被硬换行切断的句子时，结构行永不合并、上一行以句末标点结尾不合并、
   上一行是"第X条"短行不合并；
3. 项序号必须存 `item_idx` 整数并按 `(paragraph_no, item_idx)` 排序——
   按字符串排会得到"一、三、二、四"（三 U+4E09 < 二 U+4E8C，码位不撒谎）；
4. `cn2int("一千二百六十")=1260`，`int2cn(667)="六百六十七"`（生成 article_label 用）。

**审计 `audit.py`**：替代"10% 人工抽验"的**全自动强检查**——把解析结果 `render_article()`
拼回文本、剥掉空白和（一）标记，与源文本逐条比对。158/158 行全等才算过。
报告如实写明：这只证明"没丢字没串条"，**不证明源文本=官方原文**（后者需
`import_law_text.py` 导入 FLK 原件后升级 VERIFIED——申报前必做项）。

**建库主流程 `build_sqlite.py`**：按上面的顺序串起来；`--from-raw` 表示以
`data/raw/*.txt` 为源（人工校对/官方替换后重入库的通道就是这么设计的）。

### 7.4 向量检索栈（embed / store / rerank / build_vector / c_semantic）

**编码器 `embed.py`**：BGEEmbedder 封装 sentence-transformers，
**关键口径**：bge 系列要求查询侧加指令前缀 `"为这个句子生成表示以用于检索相关文章："`
而文档侧不加——写错会明显拉低召回，所以 API 故意拆成 `encode_queries` / `encode_documents`
两个方法，不给调用方犯错的机会。兜底 `HashingCharEmbedder`：纯 numpy 的 1/2/3 字
blake2b 哈希 + 次线性 TF + L2 归一，512 维，离线永远能跑，但 `name` 会被写进溯源。

**存储 `store.py`**：`ChromaStore`（cosine 空间，遥测关闭）与 `NumpyStore`
（`.npy`+`.jsonl`，暴力精确余弦）同一接口 `add/query/count`，`get_store()` 探测降级。
1295 条的规模，numpy 后端毫秒级，完全够用——**向量库是可替换件**这个判断要记着。

**重排 `rerank.py`**：候选 top_k×3=24 进，按 `0.6·BM25归一 + 0.25·字符覆盖率 + 0.15·结构命中`
重打分出 8 条。结构命中=查询里的"第X条"数字与文档条号/案号有交集就给 1.0——
法律检索里"条号对上了"必须压过一般词面相似。分词优先 jieba，缺则字符 bigram。

**通道 C 封装 `c_semantic.py`**：`Retriever` 惰性加载编码器与库（import 不付加载成本）；
`retrieve()` 加 `threading.Lock` 整体串行——chromadb 客户端与 ST 会话不是线程安全的，
而检索只 ~50ms（相对生成 10s+ 可忽略），**锁检索不锁生成**是这里的正确并发姿势。
命中文本拼成 context 时每条前打标签：`[民法典第六百六十七条]` 或 `[案号 案由]`，
截断 300 字，空行分隔——这些格式会直接进 prompt，影响答案质量。

### 7.5 ★ llm_base.py + deepseek_llm.py —— 大模型后端与"四兄弟"降级链

四个后端实现同一接口（`generate` / `generate_stream` / `draft_logprobs` / `describe`）：

1. **DeepSeekLLM**（**可选加速**，`channel/deepseek_llm.py`，D30）：调 DeepSeek 官方 API
   （OpenAI 兼容 `/chat/completions`；**只有 `base.yaml: llm_backend = deepseek` 时才生效，
   现行默认是 `hf`，不用它**）。三处与本地后端根本不同——**没有 tokenizer**（直接吃
   `messages` 数组，缓存键里存的是 messages 的 JSON）、**没有权重**（`describe()` 报地址/模型/
   思考开关/累计 token）、**网络会失败**（401/402/429/5xx/超时都转成人话报错 + 指数退避重试）。
   默认**关思考**：这个模型默认先写一大段推理，`max_tokens` 小的时候正文会是空字符串（实测踩过）。
   它的 `draft_logprobs()` 会**强制开思考**才拿得到真实分布，并检测"退化分布"（全 0.0 / 全 −9999）
   后抛错换源，绝不用假分布算出一个看起来正常的 u。
2. **HFLLM**（**现行默认**）：transformers 加载本机权重（现行默认权重 = `models/Qwen3-4B`）。
   CPU fp16（`base.yaml: dtype: float16`）；CUDA 时尝试 4bit
   （bitsandbytes），失败降级 fp16。**贪心参数**：`do_sample=False`，
   且 temperature/top_p/top_k 显式置 None——防止 transformers 5.x 对采样参数的告警/意外。
3. **VLLMLLM**（部署路径，本机无 vllm 未实测）：接口完全同 HFLLM，router 零改动。
4. **ExtractiveLLM**（规则兜底）：**不是模型**，从 context 里按词面重叠挑 3 句拼答案；
   `backend="rule_based"` 强制出现在所有溯源里，绝不允许冒充神经输出。

`get_llm()` 的降级链（D30 后多了一层、顺序有变）：配置是 `deepseek` 时
**先用 API** → 失败才 HF → 失败才 VLLM → 失败才 Extractive，每一步失败原因都 print 出来。
显式要求 API（`prefer="deepseek"`）时**不静默换模型**，失败直接抛异常——
"改了配置却跑出另一套结果"这种坑不允许再出现。
**永远能跑通链路，但降级必须在结果中标注**——这是全项目反复出现的诚实性模式。

**Prompt 构造**（通道 A/C 的答案质量半决于此）：

```
system: 你是法律咨询助手。回答必须准确、简洁，并在引用法律条文时注明法律名称与条号。
        若参考资料不足，应明确说明不确定，不要编造法条或案号。
        （通道 C 追加：【参考资料】{context}\n请优先依据上述参考资料回答…）
history: user/assistant 交替回放
user:  当前问题
→ 用 tokenizer.apply_chat_template(msgs, add_generation_prompt=True) 渲染
```

**草稿 `draft_logprobs(k=20)`**：同样的 chat template（**不带 context**），
`generate(max_new_tokens=20, output_scores=True)`，逐位置取 top-20 logprob 分布存进
`DraftStats.logprobs`（list[位置]，每位置 list[(logprob, token)]）。草稿也进缓存
（kind=`draft20`），E0 复跑秒过。

**流式 `generate_stream`（本项目最精妙的一段实现）**：
`model.generate()` 是**阻塞**的——它自己把 token 塞进 `TextIteratorStreamer` 的队列。
所以必须：**后台线程跑 generate，主线程 for piece in streamer 边收边 yield**。
三个不能改的对齐点（改任何一个，"流式和整段结果不同"）：
①同一把缓存键；②同一套贪心参数；③同一个 `build_prompt`。
线程里的异常**必须搬回主线程重抛**（`box["error"]`），否则上层只见"流莫名断了"。
缓存命中时把全文切成 8 字符小片 yield——算力为 0 但前端渲染路径与真流式完全一致
（同一套代码，不维护两条 UI 路径）。

### 7.6 ★ gate/ —— 闸门五件套（整个系统最有故事的部分）

#### intent.py —— 意图检测（纯正则，零模型）

顺序执行 7 步，全程确定性，**这就是可审计的第一层**：

1. **案号**：`RE_CASE_NO` = `[（(\d{4})[）)](1~3汉字+数字)([民刑行知执])(初|终|再|申|执|督)?(\d+)号`
   抽出→规范化为"（2022）沪01民终12345号"并解析出省份/类型名；
   "看起来像案号但代字含 测/假/编…" → 也置 hit_case_no（parsed 留空，交给核验器判"格式非法"）。
2. **法律名**：读 `law_alias` 表（兜底内置词典），**长别名优先**匹配
   （否则"民法典时间效力规定"会被"民法典"截胡）。记下别名结束位置（D26-1 用）。
3. **条号**：`RE_ARTICLE_REF` 匹配"第X条第Y款（Z）"（X 支持中文数字，`cn2int` 转换）。
   **D26-1 补丁**：口语"婚姻法32""公司法47"（法名后紧跟数字）也认，但带三道守卫：
   `(?!\d)` 防"2021年"被啃成条号"202"；`(?!\s*[年月日])` 防年份；
   `_plausible_article_no` 限 1~2000 且排除 1900~2100（民法典最长才 1260 条）。
4. **主题词**：`topic_keyword` 表（民间借贷/劳动争议/…8 主题，各十几个口语关键词）。
5. **两个问句标记**：时效词表（"现在/废止/还有效吗"…20 个）→ `temporal_query`；
   法条索取词表（"哪条/依据/怎么规定/有哪些"…21 个）→ `provision_seeking`。
6. **槽位继承（多轮的关键）**：倒序扫历史，**只继承 `trace.channel=="B"` 的轮次**里
   已确认的 `topic/law_short`。为什么这么苛刻？B 的槽位是"从用户原话正则抠出+查库确认过"的，
   而 A/C 的答案里抓词会把模型幻觉继承下来滚雪球。所以 UI 的 history 必须带 trace 传回
   （D26-4 修的就是这个链断在 pydantic 丢字段上）。
7. **完整性判据（四取一）**：`case_no` | `law+article` | `law_validity`（法名+时效问句，D12 补）
   | `topic+provision_seeking`（**必须双条件**——D10 修的就是手册原版单用 topic，
   把"什么是离婚冷静期"这种概念题误送进查库通道）。

#### draft.py + draft_source.py —— 草稿从哪来（D30 引入来源链；D38 起默认回到"同源"）

`draft.py` 不自己加载模型，只把 LLM 实例薄封装一层。**草稿与正式生成共享同一模型实例与前缀 KV**
（拆两个实例 = 预填充成本翻倍），这个约束直接决定了模块结构。

**现行默认（D38）走的正是这条直路**：`base.yaml` 把 `causal_model` 与 `draft_model` 都钉在
`models/Qwen3-4B`，`build_draft_source()` 见到"回答模型不是 API 后端"就直接返回一个来源名为
**`answer_model`** 的单来源链——草稿就是回答模型自己写的前 k 个 token（手册 S3.5 原设计），
`draft_source` 那个开关根本不参与决策，也不额外加载第二份权重。

**只有当回答模型搬到云端 API 之后，这条直路才不成立**（D30）：API 不给可用的 logprobs
（关思考时是 0.0 / −9999 占位符；开思考时给的是"我们需要回答用户…"这种**套路化推理前缀**的分布，
实测平均裕度 9–11 nats → u 全挤在 **0.0000–0.0012**，门控信号失去区分度）。
那时才启用 `channel/draft_source.py: DraftSourceChain`，按**来源链**取草稿：

| 顺序 | `trace.draft_source` | 谁在给信号 | 实测 |
|---|---|---|---|
| 现行默认（本地回答） | `answer_model` | **回答模型本身**（Qwen3-4B，共享 prefill，不额外加载） | 待 `scripts/check_draft_u.py` 实测（D38） |
| 1（切 API 后默认） | `local` | 本机草稿模型 `models/Qwen3-4B`（惰性加载）；历史上是 `Qwen/Qwen2.5-0.5B-Instruct` | 0.5B 当时：0.016 / 0.026 / **0.363** / 0.079 |
| 2 | `api` | 回答模型自己的 API logprobs（强制思考模式 + 退化检测） | u 塌缩到 0.0000–0.0012 |
| 3 | `rule` | 词面构造的确定性伪分布 | 只是让链路能跑通 |

换源过程逐条留痕（`draft_source` / `draft_attempts` / `draft_seconds`），
开关是 `configs/base.yaml: draft_source` 或 `LAWGATE_DRAFT_SOURCE`（仅在切 API 回答时起作用）。
⚠️ **换源会改变 u 的分布尺度**，而阈值 τ_b 还是旧草稿模型上校准的——
对默认 hybrid 路由无影响，但会影响 TARG 基线，重跑 E1/E2 前先看 u 分布
（跑 `scripts/check_draft_u.py`，见 5.4 与 D30/D38）。

#### signal.py —— 从草稿读"心虚"

四个信号，全部**映射到 [0,1] 且无新增可调常数**（手册原版没解决量纲问题，
实测 margin 原始值落在 −4~−1.8，固定网格阈值 0.01~0.5 会永远不触发检索——rr=0 的真实事故）：

```
margin   u = exp(−mean(top1_logprob − top2_logprob))   # 默认信号；自信→0.05 犹豫→0.82
entropy  u = mean(H(top20分布))/log(k)                  # 分布越平越不确定
variance u = V/(1+V),  V=Var(前8个位置的top1 logprob)
neglogp  u = N/(1+N),  N=−mean(top1 logprob)
```

聚合只看**前 8 个 token**（DEFAULT_M=8）：门控只要前缀信号，越往后草稿越"顺流而下"。
方向统一为"不确定性，越大越该检索"（D11），并保留 `*_confidence` 对照版本。
`raw_*` 原始量也全部落盘，供 E0 论文附录。

#### complexity.py —— 确定性复杂度评分

加权求和再夹到 [0,1]，特征全部可解释、逐项进 trace：

| 特征 | 触发条件 | 权重 |
|---|---|---|
| long | 问题 > 30 字 | +0.30 |
| case_word | 含"案例/判决/怎么判/裁判规则" | +0.30 |
| topic | 命中主题词典 | +0.20 |
| multi_turn | 有历史 | +0.10 |
| compare | 含"区别/能不能/是否/谁承担/上限…" | +0.10 |
| category_prior | 元数据类别 case→+0.30 / temporal_trap→+0.20 | +0.20~0.30 |
| boilerplate_penalty | 像"背诵条号原文"的问法 | **−0.30**，且明确给了条号再 **−0.20** |

权重人工定死、**故意不调参**——调参就把它变成第二个不可解释黑箱（模块注释原话）。
诚实披露：E0 量出它的汇总 AUC=0.861，**高于**神经信号，但这有"构造重叠"
（标签和特征都部分由类别规则生成，天然相关），引用时必须打折（D18）。

#### calibrate.py —— 分桶 + 找阈值

- 分桶优先级：基准题自带 bucket → 有历史=b4 → 有时效标记/条号=b2 → provision=b2
  → case=b3 → 其余 b1。
- 网格 `GRID = 0.01…0.50 (50档)`（`--grid-max` 可放大到 1.0，校准事故 D20 的修复）。
- 目标：**acc(τ) ≥ acc_AlwaysRAG − δ (δ=0.005)** 的约束下取 **τ 最大** 的可行点
  （`largest_feasible`）。为什么取最大而不是手册原写的"最小"？
  判据是 `u > τ → 检索`，τ 越小搜得越多，手册方向会把检索率顶到 100%，
  与"检索下降 ≥40%"的核心指标自相矛盾（D13，影响核心结论的修正）。
  手册原式保留为 `smallest_feasible` 供消融，两种结果都写进报告。
- 无可行解时：取离目标精度最近的工作点（同精度取检索更少者），`feasible:false` 如实入报告。
- `tau_scales()`：四个桶同乘 0.5/0.75/1.0/1.25 → Pareto 头图四个工作点。
- 加载：`load_taus()` 读 `configs/thresholds.json`；文件不存在时全部回退 0.10
  （**不会崩，但会悄悄退化**——复现时看到检索行为怪先查这个文件在不在）。

### 7.7 ★ 通道 B（b_structured / b_temporal / b_case_verify）—— 确定性之王

**b_structured.py**：`run(slots, query, as_of)` 按四条互斥路径，**返回 None = 查无此条/槽位不全
→ router 自动降级走门控**。全程 0 次检索、0 次模型调用、毫秒级：

- **P1 案号核验**：先 `_claimed_cause(query)`——从**案号库真实案由词表**（长词优先）里扫
  "用户声称的案由"（D26-2 教训：不能用 slots.topic 顶替，主题标签≠案由，
  否则"这案子是劳动争议，对吗？"根本抽不出 claimed → 误报核验通过）。
  核验通过后附文书信息，且**若 data_source=SYNTHETIC 自动追加溯源警示段**。
- **P2 法条+时效**：`check_provision(法, 条, as_of)` → 不安全就**绝不给原文全文**，
  只给"原条文 160 字预览 + 废止警示 + 现行替代条（含全文与来源）+ 沿革链"；
  安全则 `fetch_current` 取最新版本各款项渲染成"《民法典》第六百六十七条 …（来源：URL）"。
  `must_show_warning=True` 会一路传到前端高亮。
- **P3 法律效力询问**（D12 新增）：查"担保法现在还有用吗"这种无条号问题 →
  `check_law` + 逐条列出最多 4 个替代现行条。
- **P4 主题条文**：查 `provision_keywords` 等值 JOIN 条文表，`validity_status='现行有效'`，
  按 weight 排序去重取 8 条。**历史**：最初用 FTS MATCH，但 unicode61 分词器不切中文，
  中文查询恒 0 行、P4 自建成起从未命中过一次（D26-3，见第 9 章故事 3）。

连接口径（D28，血泪）：`conn` 不是 `__init__` 里建好的实例属性，而是
**`threading.local` 上按线程惰性建**的属性。sqlite3 连接禁止跨线程使用，
而 FastAPI 同步端点跑在线程池里，共享连接必抛 `ProgrammingError`。
`TemporalChecker`/`CaseNoVerifier` 同此办理。新增持连接的类**一律照此模板**。

**b_temporal.py 时效状态机**：
`check_law(法名, as_of)`：查沿革表（**仅精确匹配 from_law**——LIKE '%法%' 会把
"公司法(2018修正)"的旧沿革记录也捞出来，导致把现行公司法误判"已修订"，D14.1 真实事故），
取 `as_of ≥ 生效日` 的第一条 → 废止/替代="已废止"(unsafe)，修订="已修订"(unsafe)；
有未到生效日的记录 → "尚未生效"(safe，带提示)；都没有 → "现行有效"。
`_trace_chain`：BFS 收集全部后继（限深 6、去重）→ 沿革链"合同法→民法典"。
`check_provision` 五步连查：查无此条→随法废止→条文自身失效→未生效→现行有效；
SQL 必须限定 `item_no=''`，否则一条多项时款行查询会命中项行（D14.4）。

**b_case_verify.py 四级核验**：格式（解析/非法代字/年份合理范围 1990~明年/法院代字须汉字开头）
→ 存在性（查 `case_registry`）→ 类型一致（民初≠民事一审之类）→ 案由一致
（`_cause_match`：去掉"纠纷"二字后**双向包含**，"借贷"⊂"民间借贷纠纷"算一致，D15.3）。
五个出口对应 E6 的 V1~V4 标签。每次判定可写 `case_verify_log` 审计表。
**诚实声明（D15）**：合成库测不出"库里没有但真实存在"的假阴性，E6 满分是构造性满分。

### 7.8 ★ router.py —— 把一切串起来

`RouterOptions`（所有实验开关集中在这一份 dataclass，消融 E2 零复制代码）：
`signal=margin, k_draft=20, max_new_tokens=192, top_k=8, rerank=True,
disable_channel_b=False(A1), single_tau=False(A2), tau_single=0.10,
tau_scale=1.0, router_mode="hybrid", signal_buckets=("b2",)`。

**唯一的决策实现是 `_answer_events(query, history, meta, stream)`（生成器）**，
`answer()` 和 `answer_stream()` 都消费它——**彻底杜绝"界面走 B、接口走 C"的口径漂移**（D28）。
流程：

1. 解析 `meta.temporal.as_of`（只取这一个无害字段）→ `detect_intent(query, history, db)`；
2. **通道 B 早退**：`b_eligible = hit_provision | hit_case_no | slots_complete`
   且未 A1 关闭且 `slots_complete` 时试 `B.run()`；命中则产出
   `stage(channel_b)` → 一个完整 `delta`（**B 没有 token 流，查库拼装整段给，不装模作样逐字打字**）
   → `done`（含 trace），结束；
3. **门控**：`draft_logprobs(k=20)` → `u_signal=SIGNALS[signal](stats)`；
   `classify_bucket` 定桶（meta 里的 bucket 提示优先）；`complexity_score` 定 `u_cplx`；
   按 `router_mode` 选 `u` 与 `gate_source`（hybrid：b2 用信号、其余用复杂度）；
   `tau_b = taus[bucket] × tau_scale`；
4. `u > tau_b` → 先 yield `stage(retrieval)`（**检索+生成十几秒，静默就是黑屏**）→
   `Retriever.retrieve` → context；否则直接 `stage(generate)`；
5. `stream=True`：逐片 yield `delta`，join 后 strip 为答案；`False`：一次 `generate`
   产出一个 delta；
6. 最后统一 yield `done{answer, trace}`。**trace 是合同**：channel/u/u_signal/u_complexity/
   gate_source/router_mode/complexity_features/tau_b/bucket/slots(+inherited)/
   validity_status/case_verify/source_url/decision(人话判定串)/latency_ms/
   n_retrieval_calls/signal/k_draft/intent 全量/retrieval 命中明细/llm_backend/draft_text。

### 7.9 api/app.py + api/ui.py + serve_one.py + 启动服务.ps1 —— 演示层

**FastAPI（默认 8010）**，6 个端点：
`GET /health`（含实际生效模型与缓存统计）、`POST /chat`（旧行为不变，评测走它）、
`POST /chat/stream`（**SSE：stage\* → delta\* → done[→error]**）、
`POST /verify_case`、`POST /temporal`、`GET /trace/schema`（trace 字段的官方解释，答辩用）。

三条铁律（每条都是别的事故换来的）：

1. 流式端点必须是**同步 `def`** + StreamingResponse——路由生成是 CPU 密集阻塞调用，
   放进 `async` 事件循环会**卡死整个服务**；Starlette 对同步生成器自动走线程池。
2. 帧头 `media_type="text/event-stream; charset=utf-8"` + `ensure_ascii=False`——
   不写 charset 时浏览器按 ISO-8859-1 解码，中文在**前端**变乱码（上一项目踩过的坑）。
3. 生成期异常**必须成帧**为 `event: error` 再收尾，否则用户只看到"连接断了"。
   还有 `Turn.trace: dict | None` 这个字段——D26-4：pydantic 默认丢弃未声明字段，
   多轮槽位继承靠它传回，声明丢了整条继承链在 HTTP 上静默失效。

**Gradio（7860）双栏**：左栏=对照组（裸模型 `generate_stream`，不门控），
右栏=律核（`router.answer_stream` 事件驱动），下方 Trace HTML 表 + 检索命中明细 + 通道 B 步骤。
实现要点：respond_stream 是**生成器**（Gradio 每 yield 刷新一次页面）；
左栏生成放**后台线程**写 `queue.Queue`，右栏主线程在事件间隙 `_drain_left()` 取走拼接
——**两栏同时长出来**，串行会让一栏干等；右栏收工后继续取左栏尾巴直到 `end`。
刷新节流 0.06s（缓存命中时分片会一次涌出几百片，不打闸能撑爆 WebSocket）。
**两栏生成长度上限必须同一个数（192）**：唯一来源 `gen_max_tokens()←Settings.max_new_tokens`，
右栏经 `RouterOptions(max_new_tokens=mt)` 构造、左栏经 `column_max_tokens(router)` 显式传
——不靠"两处默认值碰巧相等"（D28-3）。状态行实时显示"两栏生成长度上限均 N token"。
6 个预设按钮（①废止法杀手用例 ②编造案号 ③真案号+错案由（案由从库里现取，保证演示必中）
④效力询问 ⑤纯概念题（演示"不进 B"）⑥多轮追问）。页脚的模型口径从 `provenance()` 动态生成
（防止再次写死过期型号，D21 教训）。

**serve_one.py**：ps1 的 `Start-Job` 子进程**不继承** `$env:` 修改（实测），
所以"设环境变量→起服务"固化进这个子进程脚本；`--log-file` 用 **`os.dup2` 把 fd1/2 直接接到
日志文件**——若走 PowerShell 管道，加载进度条灌爆管道缓冲区会**卡死 launch()**，
端口 300 秒不监听，还以为是模型加载慢（第 9 章故事 6）。

**启动服务.ps1**：端口占用探测（`Get-NetTCPConnection` 失灵时兜底 `netstat -ano` 解析，
否则会出现"脚本说空闲→uvicorn 报 10048→无限重启"）、崩溃自动重启上限 5、
就绪探测轮询、Ctrl+C 连坐停服。**编码**：两个 `.ps1` 必须 UTF-8 with BOM，
`启动服务.bat` 必须**纯 ASCII + CRLF**（双击打不开的两连坑，第 9 章故事 8）。

### 7.10 eval/ —— 评测体系（这套系统的"法庭"）

**benchmark.py（1900 行，规则生成器+诚实性常量）**：

## 第 9 章 设计细节与踩坑故事（9 个，每个都在代码注释里留了痕）

这个项目的工程价值一半在这些故事里。复述顺序=严重度。

**故事 1：全文检索对中文恒不命中（D26-3）**。FTS5 默认 `unicode61` 分词器
**不切中文**，一整串连续汉字算**一个** token。于是 `MATCH '利息'` 永远 0 行——
通道 B 的 P4 主题路径自建成起**从未命中过一次**，但组件级自检（直接查 SQL 构造用例）
全绿，只有端到端冒烟暴露。修复不是换分词器，而是**改走 `provision_keywords`
等值匹配**（建库时就按条文标好主题词，检索时不做分词）。教训：**涉及"中文分词"的
功能，必须写一条真实中文查询的端到端断言**。

**故事 2：sqlite3 连接不能跨线程（D28-1）**。三个类原本都在 `__init__` 里建好连接；
FastAPI 同步端点跑在 Starlette 线程池 → `ProgrammingError: SQLite objects created in a
thread can only be used in that same thread`。修法：`threading.local` + 按线程惰性
`conn` property。**同一个坑在本项目出现三次**，于是写成了全库规范。

**故事 3：服务"假死"真凶——控制台 QuickEdit（上一项目同源教训）**。Windows 控制台
鼠标点进窗口=暂停写 stdout；stdout 一堵，日志型服务整个冻住（端口在听、CPU 近零）。
所以 `serve_one.py` 用 `os.dup2` 重定向 + ps1 隐藏窗口跑服务。**永远让服务进程的输出
不依赖有人类的控制台。**

**故事 4：校准方向反了会"指标自相矛盾"（D13）**。手册写"取满足精度约束的**最小** τ"，
但判据是 `u > τ → 检索`——τ 越小搜得越多，最小可行 τ 会把检索率顶到 100%，
直接把"检索调用下降 ≥40%"的核心指标干碎。修正为取**最大**可行 τ。
教训：**先验证目标函数和自己指标的代数一致性，再抄公式。**

**故事 5：辛普森悖论（D18，E0 红灯）**。四个神经信号汇总 AUC≈0.51~0.56（红灯，
按手册该关信号门控）；分桶一看 b2=0.82 明明很好，b1/b4 严重反向——汇总时被
"标签由类别规则生成"造成的桶间失衡抵消了。处置：默认路由改 hybrid（按桶取信号），
并诚实披露复杂度评分 0.861 含构造重叠。教训：**全局指标不显著 ≠ 每个子群都不行；
但反过来，子群指标也可能来自构造，两头都要防。**

**故事 6：管道背压卡死启动**。`python | ForEach-Object | Out-File` 起 Gradio，
权重加载进度条灌满管道缓冲区 → launch() 卡在监听前 300 秒超时，日志只有几行。
手工直跑 6 秒就监听。改 `os.dup2` 文件重定向后根治。教训：**别把长命进程的 stdout
接在有人类节奏的管子上。**

**故事 7：受限沙箱里 subprocess 管道 EPERM（D20.2）**。某些沙箱禁命名管道，
`capture_output=True` 的子步骤以 EPERM **静默失败**（日志只剩一行表头）。
`run_pipeline.py` 因此加了 `--inherit-stdio`（子进程直接继承父的日志文件句柄）。
教训：**静默失败是最贵的失败，流水线必须记录每条子命令退出码**
（`docs/pipeline_steps.json` 就是这么来的）。

**故事 8：双击 .bat 起不来（两因叠加）**。①文件 LF 行尾：cmd.exe 按固定缓冲读批处理，
LF 会让它把每行**尾巴**当命令执行（屏幕上刷出 `'demo' / 'his' / 'rshell' 不是内部或外部命令`）；
②.bat 里写了中文文件名，而 cmd 按控制台代码页 CP936 读字节，UTF-8 中文路径变乱码 →
`if exist` 永远 MISSING。修法：`.bat` 纯 ASCII+CRLF，用**文件名首字符码位**（0x542F）
在 PowerShell 侧筛启动器；而 `.ps1` 恰恰相反必须 UTF-8 **with BOM**。
教训：**同一套启动链上不同文件的编码要求可以互相冲突，改动前先认清目标文件的规则。**

**故事 9：流式和整段是两份代码就会漂移（D28）**。曾担心"界面走 B、接口走 C"，
解法是把决策逻辑收敛成**唯一生成器** `_answer_events(stream)`，
`answer()` 只是消费它的便捷壳；流式与整段共用同一缓存键与贪心参数，
`check_stream.py` 离线断言同源（原 `smoke_stream.py` 真机断言"流式≡整段、双向缓存互通、
真逐 token、SSE 帧完整、中文不乱码"，该脚本 2026-09-16 删除，见 D37，结论保留为历史记录）。
教训：**一个系统同一行为只允许一处实现；测不出来就写进可复跑的自检脚本。**

## 第 12 章 FAQ

**Q1：我电脑没显卡，真能跑？** 能，而且**默认配置下就是纯 CPU 跑通的**：回答与门控草稿都用本机 `models/Qwen3-4B`（fp16，约 8 GB 内存，**全程离线**，单条 192 token 需数十秒量级；首次提问要先加载权重 1–3 分钟），外加 bge 向量编码。想快就切 API 回答（`-LlmBackend deepseek`，单条 1–3 秒，但要联网 + 计费）。要是机器上只剩 6.7B 夫子·明察兜底，18 核 CPU 上约 1 token/s、单栏 192 token 要 2~4 分钟——慢，但全功能。

**Q2：有 GPU 怎么加速？** 改三行 `configs/base.yaml`：`device: cuda:0`、`load_in_4bit: true`、
`llm_backend: vllm`（装 vllm 后）。消费级卡 + vLLM 整问约 2~7 s（README §1 有逐档估算表）。
transformers 直推在 A100 上也只有 ~40 tok/s（框架开销主导），要红利必须 vLLM。

**Q3：第一次跑通要花多久？** 装环境+下模型 0.5~2 小时（看网速）；第 1~4、7、8 步合计
约 5~10 分钟（模型加载后）；E0/校准/全量实验是"小时~天"级，**可先跳过**。

**Q4：能换更大的模型吗？** 把权重放进 `models/xxx` 并设 `$env:LAWGATE_MODEL`。注意：
换模型 → 缓存整体失效（键含模型名）→ 阈值与 E0 结论属于旧口径，严谨做法是
用新模型重跑第 5~6 步并记录在自己的复现报告里。

**Q5：法条内容我能改吗？** 三种正规姿势：改 `seed_corpus.py` 后重跑建库；
或直接把 `data/raw/《法名》.txt` 替换为官方文本再 `build_sqlite --from-raw`；
或用 `import_law_text.py`/`import_judgments.py` 导入官方原件并把 `ingest_provenance`
升 VERIFIED / `data_source` 升 CJWS。词典（别名/主题）改数据库即可，代码不用动。

**Q6：为什么我看到的检索比设计少/多？** 先看 `configs/thresholds.json` 是否是你自己
校准的、再看 `router_mode`。演示界面点"看 trace"，`decision` 字段是人话，
`u/tau_b/bucket` 三件套足够你判断闸门在哪一环。

**Q7：trace 字段谁定义的？** `router.py` 最后一块 dict + `GET /trace/schema` 的官方注释；
两端必须同步改（这是文档化的字段合同）。

**Q8：万一某组实验我没跑，图能先自己画吗？** 能：`scripts/plot_all.py --demo` 用全合成
数据自检绘图管线，**每张图自动打 DEMO 戳**，不会冒充真实结果——这个防呆请保留。
（本仓 E1–E5 已全部落盘，正常出图走 `scripts/plot_all.py --exp all` 即可。）

**Q9：想加第四条通道（比如调外部法条 API）？** 挂到 `ChannelB` 的兄弟位（确定性通道）
或独立通道+新桶；务必在 RouterOptions 加消融开关、trace 加 `n_external_calls`，
并同步更新 `/trace/schema` 与本指南第 8 章。

**Q10：这文档和 `docs/system_manual.md` 什么关系？** 手册=给评审专家的正式说明书（每个类名
都对照代码）；本文=给上手人的复现教程。两册中的类名/路径/常量一一对应，冲突时
**以代码为准、以 deviations.md 为仲裁**。
